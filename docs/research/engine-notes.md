## Ranked summary (most time-saving first)

1. **There is an in-game Attachment Editor that edits the held-item attachment live with a gizmo, a player model, and any player clip, then saves back to the script.** Debug menu (launch the game with `-debug`) -> DEV tab -> "Attachment" (`showAttachmentEditor`). It lists all ModelScripts, lets you add the player model and pick a clip (`getClipNames`), pick a bone, drag translate/rotate/scale gizmos on `offset`/`rotate`/`scale`, and "Save" calls `AttachmentEditorState.writeScript`, rewriting the model block in the script file. This replaces the tilt-calibration sweep. (CONFIRMED: `media/lua/client/DebugUIs/AttachmentEditorUI.lua`, `ISDebugMenu.lua` line 39, class `AttachmentEditorState`.) Caveat: it edits the file the script came from, so for a mod model it will write into whatever path the script loaded from; check the path it prints ("writing %s") before trusting it, and copy the numbers back into the repo.
2. **Exact attachment math is known** (area 1): for a held model the matrix is `bone_model_transform * [T(offset) * Rxyz(rotate deg) * S(attach.scale)]  * meshTransform * S(modelScript.scale)`; `rotateXYZ` = Rx*Ry*Rz (z applied first to the model), offsets are NOT multiplied by model scale, and the self-attachment is NOT inverted. This matches your "Ry(16.8) Rx(90)" recipe, so `rotate = (x y z)` with R = Rx(x)Ry(y)Rz(z) is exactly right. (CONFIRMED: classes `ModelInstanceRenderData.makeAttachmentTransform`, `AnimatedModel$AnimatedModelInstanceRenderData.transformToParent`.)
3. **Idle-state clips move the player because deferred (root) movement is applied from every live track regardless of node/state**: any track whose node has `useDeferredMovement` (default true) adds its `Translation_Data` Y-bone delta, weighted by blend weight, times `MotionScale` 1.6 (`AnimSets/Defaults.xml`). Idle only differs by name (`m_Name` containing "Idle" sets `isIdleAnim`, used for `containsAnyIdleNodes`). To stop an idle clip moving the player set `<m_useDeferredMovement>false</m_useDeferredMovement>` on the node, or keep Translation_Data flat. (CONFIRMED: `AnimationPlayer.calculateDeferredMovementAccumInternal`, `AnimNode.<init>` defaults.)
4. **`m_SpeedScale` as a variable name is read when the node's tracks START, not per frame** (`AnimLayer.startLiveNodeTracks` calls `AnimNode.getSpeedScale(source)` once; the only per-frame writer, `AdvancedAnimator.updateSpeedScale`, has no callers in the jar). So changing the variable while the same node keeps playing does nothing; it only takes effect when the node (re)starts, e.g. a tier change that switches node. That likely explains the earlier no-op speed tests besides the harness arg bug. The numeric form (`0.48`) is parsed once at load. (CONFIRMED by reading; the behavioural claim "no effect mid-node" is LIKELY since I did not run it.)
5. **Unknown `PerformingAction` plays Surrender because of `AnimSets/player/actions/default-fallback.xml`**: a condition-less node (`Bob_EmoteSurrender`, blend 0.8, speed 0.8) in the `actions` state. Node selection is "most conditions wins, ties all play", and a node with zero conditions always passes, so it is chosen when no `PerformingAction = X` node matches. Define a node with `m_Name`, `m_AnimName` and a `PerformingAction STRING = <name>` condition in `media/AnimSets/player/actions/`. In debug mode `setActionAnim` also logs `WARNING: did not find node with condition 'PerformingAction = %s' in player/actions/` (CONFIRMED: file + `AdvancedAnimator.printDebugCharacterActions`, `AnimState.getAnimNodes`).
6. **Hidden Lua-settable debug variables force a node**: `dbgForceAnim` (bool), `dbgForceAnimStateName`, `dbgForceAnimNodeName`, `dbgForceAnimScalars`, `dbgForceScalar`, `dbgForceScalar2`; they work only when the DebugOptions toggle `animation.animLayer.allowAnimNodeOverride` is on. (CONFIRMED: `AnimState.getAnimNodes`, `AnimLayer.updateInternal`.) Useful for previewing a node in the world without satisfying its conditions.
7. **Runtime reload exists and is Lua-callable**: globals `refreshAnimSets(bool)`, `reloadActionGroups()`, `reloadModelsMatching(string)`, `reloadLuaFile(path)`, `getScriptManager():ReloadScripts(...)` (debug Scripts window has a "Reload All Scripts of ScriptType" button), `getScriptManager():getModelScript("Module.Name")` returning a live `ModelScript` whose `getAttachmentById("Bip01_Prop1"):getOffset()/getRotate()` are mutable `Vector3f`s. (CONFIRMED names: `LuaManager$GlobalObject`, `ScriptManager`, `Exposer` list.)
8. **Camera/projection is fully recoverable**: pitch 30 degrees (`0.5236` rad, `rotate X`), yaw 135 degrees (`2.356` rad), orthographic, tile diamond 64*tileScale px wide x 32*tileScale tall with `tileScale = 2` (128x64 px). Details in area 2.

## Area 1: Attachment transform pipeline

**Script syntax** (CONFIRMED: `ModelScript.LoadAttachment`, `LoadVector3f`): inside `model X { attachment <id> { bone = ..., offset = x y z, rotate = x y z, scale = f } }`. `offset`/`rotate` are three space-separated floats (`String.split(" ")`, so use single spaces); `rotate` is degrees; `scale` default 1; `zoffset`, `canAttach` exist too. Model-level keys read by `ModelScript.Load`: `mesh`, `scale`, `shader`, `static`, `texture`, `invertX`, `cullFace`, `postProcess`, `undoCoreScale` (multiplies model scale by 0.6667), `boneWeight`, `animationsMesh`. Web: https://pz-wiki-modding.github.io/PZ-API-Docs/scripts/attachment.html and .../scripts/model.html agree (offset "relative to the bone", rotate in degrees; no unit given for offset).

**Matrix** (CONFIRMED: `ModelInstanceRenderData.makeAttachmentTransform`, also `ModelInstance.getAttachmentMatrix`): `M = translation(offset) ; M = M.rotateXYZ(rx*pi/180, ry*pi/180, rz*pi/180) ; M = M.scale(attach.scale)`. JOML `rotateXYZ` post-multiplies Rx, then Ry, then Rz, so on a model point p: `M*p = offset + Rx*Ry*Rz*(scale*p)`: z rotation is applied first, then y, then x. Matches the repo recipe.

**Placement chain for a held item** (CONFIRMED: `AnimatedModel$AnimatedModelInstanceRenderData.transformToParent`, `ModelManager.addEquippedModelInstance` / `ResetCharacterEquippedHands`, which pass the bone name "Bip01_Prop1" for the primary item and "Bip01_Prop2" for the secondary as `parentBoneName`):
1. start from the parent (character) matrix;
2. if the parent's ModelScript has an attachment named like the child's `attachmentNameParent` (or `parentBoneName`), use `applyBoneTransform(parent, thatAttachment.bone)` then multiply by that attachment's transform; otherwise `applyBoneTransform(parent, parentBoneName)`, i.e. the bone's current MODEL-space transform from `AnimationPlayer.getModelTransformAt(boneIndex)` (animated pose, not the skinning/inverse-bind matrix);
3. multiply by the CHILD model's own attachment transform, looked up by `attachmentNameSelf`, else by the name of the parent bone (so `attachment Bip01_Prop1 { ... }` inside the item's model script). It is inverted only if the static `ModelInstanceRenderData.invertAttachmentSelfTransform` is true; nothing in the jar sets it, so default false: the model is NOT inverse-mapped. That is why "offset = where the model's origin lands in the hand frame";
4. post-multiply the mesh's own transform (`ModelMesh.transform`, from the file);
5. finally scale by `ModelInstance.scale` = `ModelScript.scale` (set by `applyModelScriptScale`).
Consequences: the attachment `offset` is in bone units and is NOT scaled by the model `scale`; the attachment `scale` scales only the mesh (it comes after the offset in `T*R*S`); the model `scale` scales the mesh after everything. `ModelScript.scaleAttachmentOffset(f)` exists (multiplies all offsets) but is not called by `Load`, so there is no implicit offset scaling. Units: character space, same units as the meshes (Bob mesh is about 0.98 tall, see area 2).

**Weapons/hands** (CONFIRMED file): vanilla weapon models define `attachment world` (used for items on the ground) and `attachment Bip01_Prop2` etc. (`media/scripts/generated/models_weapons.txt`: e.g. SaucePan `offset = -0.0131 0.0078 0.0007`, `rotate = 180.0 -11.9336 180.0`), so vanilla also hand-tunes the hand frame per model; the character body model `MaleBody` has its own attachments with `bone = Bip01_R_Hand` (bags) in `models_characters.txt`. Primary-hand item uses Bip01_Prop1, secondary Bip01_Prop2 (`ModelManager` constants).

**What Bip01_Prop1 does in animations**: it is an ordinary bone of the Human skeleton (listed in `SkeletonBone`, `AnimNode` hand-bone weights; `AnimNode.Parse` adds `Bip01_Prop1`/`Prop2` to default sub-state bone weights), so its pose is whatever each clip keys; the held model follows the bone's animated model transform every frame, which is why a clip that rolls it 16.8 degrees tilts the item. Clips that must not tilt the item can key Bip01_Prop1 explicitly (already noted in memory). UNVERIFIED: why vanilla bone is rolled in the riding pose (clip data, not engine).

## Area 2: Camera, projection, facings, scale

**World-iso camera** (CONFIRMED: `Core.DoPushIsoStuff`): orthographic; modelview = `scale(Core.scale * tileScale/2)` * `rotateX(0.5235988 rad = 30 deg)` * `rotateY(2.3561945 rad = 135 deg)` then translate by the object world position minus camera. `Core.tileScale = 2` (set in `Core.<clinit>`), `Core.scale = sqrt(2)/2/10/1.5 = 0.047140`, and `getZoom(player) = offscreenBuffer.getDisplayZoom * tileScale/2` (so zoom 1.0 is the default, min/max from `MultiTextureFBO2`, mouse-wheel via `Core.doZoomScroll`). Projection half-extents are `offscreenWidth/1920/2`, i.e. 1920 px reference width.
**Offscreen character camera** (CONFIRMED: `CharacterModelCamera.Begin`, used for imposters, UI portraits and the Animation Viewer "isometric" option): ortho +-42.75 x +-42.75, translation (0, -0.45, 0), `rotate(30 deg about X)` then `rotate(facingAngle + 45 deg about Y)`.
**Screen mapping** (CONFIRMED: `PlayerCamera.XToIso`): `X = (sx + 2*sy) / (64*tileScale)`, hence `sx = 32*tileScale*(X-Y)`, `sy = 16*tileScale*(X+Y)`; with tileScale 2 a 1x1 tile is a 128x64 px diamond (a 2:1 dimetric; sin 30 deg = 0.5 explains the 2:1). Z levels: `+3.0 * z` tile units in the inverse (`XToIso(..., z)` adds `3*z`), i.e. one floor = 3 tiles of height.
**Pixels per model unit at zoom 1** (LIKELY, derived): `Core.scale * 1920 = 90.5 px` per unit before rotation; a unit along world x moves 64 px horizontally; model +Y (up) projects to `cos(30 deg) * 90.5 = 78 px` per unit. So 1 model unit equals 1 tile edge in the horizontal plane, and the 0.98-unit Bob is about 77 px tall at zoom 1 unless the character gets an extra scale I did not find. Please verify against a screenshot: if Bob's feet-to-head is about 77 px at zoom 1 the formula is right. (The memory note "1 unit ~ 2 m" is consistent with Bob = 1.8-2 m and a tile = ~2 m of horizontal space? UNVERIFIED.)
**Bob mesh bounds** (CONFIRMED, measured from `media/models_X/Skinned/MaleBody.X`, 617 verts): x +-0.493, y -0.0009..0.980, z -0.060..0.122 (arm span 0.99, height 0.98 in game units).
**Facings** (CONFIRMED: `IsoDirections.<clinit>`): N=(0,-1), NW=(-1,-1), W=(-1,0), SW=(-1,1), S=(0,1), SE=(1,1), E=(1,0), NE=(1,-1) as (dx,dy) in world x/y; `angle = ordinal * 2pi/8` with N=0, NW=45 deg, W=90, SW=135, S=180, SE=225, E=270, NE=315; `fromAngle(x,y) = safeFromAngle(atan2(y,x))`. Consistent with your note that keyboard S faces the screen (world +x,+y = SE vector), and pure world S (+y) is bottom-left on screen (sy = 16T*(X+Y)). Character model yaw uses `facingAngle + 45 deg` in the offscreen camera and the world-iso camera's 135 deg yaw, so the model faces its movement vector as `atan2` of the world (x,y) direction; fit a Blender render to match by using pitch 30 deg, yaw 135 deg, ortho.

## Area 3: Animation system

**Structure** (CONFIRMED files): `media/AnimSets/player.xml` filters clip/folder prefixes `Bob_`/`Kate_`; each folder under `AnimSets/player/` is a STATE with one XML per NODE; `media/actiongroups/player/<state>/` holds state transitions (`to_*.xml`, `defaultTransitions.xml`); `AnimSets/Defaults.xml` holds `MotionScale 1.6`, `RotationScale 1.1`. Node fields (class `AnimNode`, defaults from `AnimNode.<init>`): `m_Name`, `m_AnimName` (clip file name without extension in `anims_X/Bob`), `m_Priority` (default 5, passed to the track; highest wins when tracks overlap), `m_ConditionPriority`, `m_BlendTime`, `m_BlendOutTime` (default -1 = use blend time), `m_Looped` (default true), `m_SpeedScale` (float or variable name, default "1.00"), `m_SpeedScaleVariable`, `m_Scalar`/`m_Scalar2` (variables driving 2D blend), `m_2DBlends`/`m_2DBlendTri`, `m_Conditions`, `m_Events`, `m_Transitions`, `m_SubStateBoneWeights` (layer mask on named bones), `m_DeferredBoneName` (default "Translation_Data"), `m_deferredBoneAxis` (default Y), `m_useDeferredMovement` (default true), `m_useDeferedRotation`, `m_deferredRotationScale`, `m_StopAnimOnExit`, `m_EarlyTransitionOut`, `m_SyncTrackingEnabled`, `m_TrackTimeToVariable`, ragdoll and grapple fields. Condition types: STRING, BOOL, INT, FLOAT, OR, EQU, NEQ, STRNEQ, GTR, LESS (web: https://pz-wiki-modding.github.io/PZ-API-Docs/xml/animnode.html).
**Node choice** (CONFIRMED: `AnimState.addNode`, `AnimState.getAnimNodes`, `AnimNode.compareSelectionConditions`): the state's node list is kept sorted so higher `m_ConditionPriority` first, then MORE conditions first (abstract nodes are held apart). `getAnimNodes` walks that list, takes the first node whose conditions all pass, and also adds every following node that compares EQUAL (same condition priority and condition count), stopping at the first strictly lower one. So specificity wins, ties play simultaneously (blended). A node with no conditions (default-fallback) matches always but loses to any more specific match. A node whose state's list is empty plays nothing.
**Blend**: node `m_BlendTime` fades the node in; `m_BlendOutTime` out; `m_Transitions` (with optional `m_AnimName` transition clip and `m_Conditions`) apply when leaving to a named target node; `m_SubStateBoneWeights` masks bones per node (the emote nodes use it to leave the legs alone).
**Deferred movement / Translation_Data / speed** (CONFIRMED: `AnimationPlayer.calculateDeferredMovementAccumInternal`, `ImportedSkeleton.processAiScene`, `IsoGameCharacter.doDeferredMovement`): `Translation_Data` is a bone node added to the skeleton by the importer. Each frame, for each live track from highest priority down, with a running weight budget starting at 1: if the track is not finished, not ragdoll, has `useDeferredMovement`, its frame-to-frame deferred-bone delta (Y axis by default, from the clip) is added scaled by `min(deferredBoneWeight * blendWeight, remaining)`; the sum is rotated into the character facing, multiplied by `MotionScale` (1.6), and `IsoGameCharacter.doDeferredMovement` applies it as the movement (path-follow states clamp it). So travel speed = (Translation_Data translation per second in the clip) x track speedDelta (m_SpeedScale) x 1.6, not a "speed" variable; `setSpeedMod`/`setSlowFactor` feed other modifiers (`updateSpeedModifiers`, run speed) rather than this accumulation, which fits the pogo observation. The Animation Viewer has a `useDeferredMovement` toggle (`setCharacterUseDeferredMovement`).
**Why idle can move you**: nothing in the accumulation checks state or `isIdleAnim`; any live track with deferred movement moves the character. Turn it off per node or keep the Translation_Data bone still.
**m_SpeedScale**: float -> `speedScaleF`; non-numeric -> `speedScaleVariable` and `getVariableFloat(name, 1)`, sampled when tracks start (summary item 4). `Anim2DBlend` has its own `m_SpeedScale`.
**Action nodes** (CONFIRMED): `BaseAction.setActionAnim(name)` sets the animation variable `PerformingAction = name` and `IsPerformingAnAction = true`, and enters `PlayerActionsState` (sub-state `actions`); nodes in `AnimSets/player/actions/*.xml` match with `<m_Name>PerformingAction</m_Name><m_Type>STRING</m_Type><m_Value>Name</m_Value>`. If none match, `default-fallback.xml` plays (Surrender). Lua: `ISBaseTimedAction:setActionAnim("Name")`, `setAnimVariable(key,val)` (set on action start, cleared with the action), `setOverrideHandModels`. 288 files in that folder, so copy an existing one (e.g. `Bandage.xml`) as a template.

## Area 5: Worn item models (skinned clothing)

**Item -> model** (CONFIRMED: `media/clothing/clothingItems/Apron_Black.xml`): `<clothingItem>` with `m_MaleModel`/`m_FemaleModel` (path under `models_X`, e.g. `skinned\clothes\bob_apron`), `m_Static` (false for skinned), `m_AttachBone` (bone name for static/attached items), `textureChoices`, tint/hue flags, `m_GUID`. Static models use `m_AttachBone` and the model script attachment; skinned ones are drawn as part of the character's model slot.
**Binding** (CONFIRMED by reading `ImportedSkinnedMesh.processAiScene`): per vertex 4 bone indices + 4 weights taken from Assimp `AiBone.getBoneWeights`, bone name -> index via the BASE skeleton's `boneIndices` (`ImportedSkeleton`); weights renormalised to sum 1 (`1/sum` factor); vertex positions, normals, UVs stored as-is; the clothing file's own `AiBone` offset (inverse bind) matrices are never read (no `getOffsetMatrix` in this class; `getOffsetMatrix` appears only in `ImportedSkeleton`, i.e. the skeleton/animations mesh of the base character). Skinning then uses the base skeleton's bind pose, so a clothing mesh is only correct if its vertices are in the same rest pose/space as the base `Human` skeleton mesh (`animationsMesh = Human` for `MaleBody` in `models_characters.txt`). Root node found by name `Dummy01` (or `VehicleSkeleton`); `Translation_Data` is added as an extra bone. A clip/mesh missing a Frame/skeleton tree fails to load as already seen (ties to memory: needs Frame tree + mesh + material + SkinWeights).
**Draw**: `AnimatedModel.addClothingItem` / `populateCharacterModelSlot` adds the model as a ModelInstance in the character's slot; the matrix palette (one 4x4 per bone, 960-float buffer) is the skinning transform array `AnimationPlayer.getSkinTransforms`, rendered by the skinned shader (`DrawChar`). Texture from `textureChoices` / `ModelInstance.tex`, tint from `ItemVisual`.
