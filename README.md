# Impractical Transport (Project Zomboid, Build 42)

Ridiculous, strictly worse ways to get around. First transport: a pogo stick. Planned: tricycle, roller skates, unicycle, stilts, an inflatable ball with handles.

Layout follows the B42 workshop format: `Contents/mods/<id>/{common,42}`. Build-specific files live in `42/`; if a patch breaks something, copy `42/` to `42.x/` and fix only there.

## How a transport works (no Java, no real vehicles)
It follows the pattern of the Bicycle and Kick Scooter workshop mods: a **held item** plus **animation nodes** plus a little **client Lua**.
- `media/scripts/ImpracticalTransport_items.txt`: the item (two-handed, so it sits in the primary hand).
- `media/scripts/ImpracticalTransport_models.txt`: the model and where it attaches to the hand (`Bip01_Prop1`). Placement formula: a model point `p` ends up at `offset + rotate(p)` in the hand's frame (X right, Y forward, Z up in the idle pose).
- `media/AnimSets/player/{idle,movement,run,sprint}/*_pogo.xml`: animation nodes that only play while the variable `PogoActive` is true. Their playback speed comes from `PogoWalkSpeed` / `PogoRunSpeed`; the clip's `Translation_Data` track is what moves the character (speed = distance per hop / hop time x speed scale).
- `media/lua/client/ImpracticalTransport.lua`: sets those variables from the held item every tick, drains endurance (less with Fitness), slows a winded rider, and blocks aiming and melee while the stick is held. Adding a transport = a new profile entry + item + model + clip.
- Riding state is derived from the held item each tick, so there is nothing saved to migrate across patches.

## Assets are generated by scripts (Blender 4.1, headless)
- `tools/blender/pogo_stick.py`: builds the stick from primitives, writes `models_X/ImpracticalTransport/PogoStick.X` (game units, Y up, text DirectX format like vanilla item models) and preview PNGs. `GAME_UNITS_PER_METRE` sets the size (the survivor's arms are short, so the stick is larger than life).
- `tools/blender/zomboid_x.py`: reader for the game's text `.X` files (body, Bob animations) plus a Blender importer. The armature rest is the **skin bind pose** (T-pose), not the frames' first pose; keep that, it is what makes vanilla clips look right.
- `tools/blender/pogo_hop.py`: poses the survivor with a two-bone solver (feet on the pads, hands on the grips) and writes the clip `anims_X/Bob/Bob_PogoHop.X`, then reads it back and renders `previews/pogo_hop_*.png` as a round-trip check.
- `previews/` is git-ignored (it renders the game's own player model).
Run any of them with `"C:\Program Files\Blender Foundation\Blender 4.1\blender.exe" -b -P tools/blender/<script>.py`.

## Testing
`scripts/smoke_test.py` reuses the launch, auto-login and channel code of the `project-zomboid-rl-based-players` repo (set `PZ_RL_REPO` if it is not at `C:\bench\project-zomboid-rl-based-players`).
- `python scripts/smoke_test.py static`: files only (mod.info, every mesh and texture the scripts name exist).
- `python scripts/smoke_test.py server`: boots a dev server with the mod and scans its log (about 5 minutes).
- `python scripts/smoke_test.py play --keep`: also starts a graphical client, teleports to an open field, gives the item as admin, measures bare-hand walking vs the pogo, checks that a real unequip action works, and leaves the game open with the stick equipped.
- Stop everything afterwards: `python <RL repo>/scripts/cleanup.py`.
Lessons baked into the test: the server checksums scripts, so any mod edit needs a full server boot; items must be added server-side (`/additem`), and hands must only change through real equip/unequip actions, or the server and client disagree and nothing can be equipped.

## Status (2026-10-31)
Smoke test passes: the item loads and equips, the hop clip loads (bare walking ~1.4 tiles/s, pogo ~0.8), a real unequip action works, endurance drains. Not yet seen by a human: how the hop animation looks, whether the right hand sits on the right grip (the sideways offset sign is a guess; flip `offset.x` if it is on the wrong side), and that aiming/swinging is blocked.

Gotchas learned the hard way: the game loads clips with Assimp, so a clip needs the skeleton Frame tree, a mesh with a material, and SkinWeights naming the bones (without skin weights the server aborts at boot). The armature rest must be the skin bind pose, not the frames' first pose.
Human test 2026-10-31: hop looks good, aim/swing are blocked; the stick floated away from the rider (fixed since: hands and the Prop1 bone keep their Bob_Idle orientation, and the rider leans 12 degrees forward, `LEAN_DEG` in `pogo_hop.py`).
Done since, not yet seen by a human: mount/dismount clips (`Bob_PogoMount/Dismount`, nodes in `AnimSets/player/actions/`, driven by the `PogoTransition` variable), multi-colour palette texture and a generated inventory icon.
Human findings from the rotate calibration (round 1): the attachment's `rotate` composes z first, then y, then x; y spins the stick about its own axis, z lays it sideways, x tilts it fore and aft. The 78 rotate I tried as a forward lean showed up slanted (bottom out to one side, left foot on the spring), so the lean may be going the wrong way.
Stick rotation (done by screenshot, 2026-10-31): round 2 of the calibration, run by `python scripts/calibrate_shots.py` (rest facing four ways plus a wide circle, like the human test), picked `rotate = 102 0 0` (78 and 66 lean sideways, 114 leans the other way, 90 is close); offset recomputed for it. The `PogoCal` sticks are removed; regenerate with `python tools/make_calibration.py` and `python scripts/calibrate_shots.py` for a finer sweep (96 and 108 if 102 looks off).
Human testing queue (do when the user is back): check mount/dismount, the new icon and colours, run and sprint, terrain slowdown and a stumble in real play (the rider falls forward, `ImpracticalTransport stumble` in the client log), and that the stick fits at 102 by eye.
Dev queue: spring compression (researched 2026-10-31: vanilla `animationsMesh` is used only for characters, animals and animated world objects, so a skinned held item looks unsupported; the workable route is two models, the upper stick on the primary hand `Bip01_Prop1` and the pads and spring as a companion item in the secondary hand `Bip01_Prop2`, with the hop clip moving the Prop2 bone relative to Prop1. Risks: the companion must be equipped through real server-validated actions (the harness traps in the memory notes apply), a two-handed item currently blocks the second hand, and nothing has been tried in game); foot-in-other-hand carry pose; left-hand grip (`Bip01_Prop2`).
Terrain (built, untested by a human): the hop speed is multiplied by the engine's walking slowdown (`WalkSpeedTrees`, `getSlowFactor`) and by a ground table (`SURFACES` in `ImpracticalTransport.lua`: sand, mud, water, gravel, dirt, grass); bushes and trees raise the stumble chance. Unrecognised ground prints `ImpracticalTransport unclassified ground: ...` once in the client log; add it to the table. The numbers are placeholders.
Run and sprint (built, untested by a human): they play the same hop clip faster (run 1.7x, sprint 2.2x, ratios estimated from vanilla and not measured), with 3x / 6x the trip chance and 1.6x / 2.5x the endurance drain. Human check: hold run and sprint, confirm the hop speeds up, falls are clearly more frequent, and the stick does not detach at speed. Dev follow-up: measure vanilla's walk/run/sprint ratio and tune.
Idea journal, explore later: **physical terrain failure** (option D). On loose ground (mud, sand, shallow water) a hop can fail outright: the rider sinks, the hop restarts, the stick gets stuck for a moment, rather than only moving slower. It would reuse the stumble hook with a new "stall" animation (or the stumble as a stand-in first), and needs a human to tune how often and how long.
